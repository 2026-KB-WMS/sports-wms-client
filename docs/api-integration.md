# API 연동 가이드 (프론트 쪽 합의)

API 계약 본문은 wms-server의 `docs/api/*.md`가 기준이다([README](../README.md#api-계약-서버-문서가-기준) 참고). 이 문서는 **서버 문서에 없는 프론트 쪽 합의와 연동 현황**만 적는다. 서버 문서의 내용을 복제하지 않는다.

## 1. 코드 규칙

- `app/lib/api/<도메인>.ts`: 엔드포인트 함수와 요청·응답 타입. 서버 명세의 필드명을 그대로 쓴다(camelCase).
- `app/features/<도메인>/hooks.ts`: TanStack Query 훅. 쿼리 키는 `["도메인", 리소스, 조건]`.
- `app/features/<도메인>/*-page.tsx`: 화면. 라우트는 `app/routes.ts`에 등록한다.
- 호출은 `apiClient`만 쓰고(응답 봉투는 이미 벗겨짐), 오류는 `ApiError`(`statusCode`, `errorCode`, `fieldErrors`)로 다룬다.
- 4xx는 재시도하지 않는다(`query-client.ts`).

## 2. 서버 현황에 따른 임시 처리

서버가 아직 구현하지 않은 부분을 프론트가 어떻게 다루는지 정해 둔다. 서버가 바뀌면 이 절을 갱신한다.

| 서버 현황 | 프론트 처리 |
|---|---|
| 인증(JWT) 로그인 연동 완료(#31). 토큰은 `app/lib/auth-token.ts`가 저장하고 `client.ts`가 `Authorization: Bearer`로 붙인다 | 401은 토큰 삭제 후 `/login`으로 이동(`AuthGate`). 로그인·가입의 401은 제외 |
| ~~처리 사용자를 쿼리 파라미터 `userId`로 받음~~ → 서버가 토큰에서 채움(#170) | 클라이언트는 `userId`를 보내지 않는다(#32). `/warehouses/my`·`/stores/my`도 토큰 기준이다. `useCurrentUser()`는 화면 표시·작성자 비교용 사용자 정보만 준다 |
| 역할별 403이 동작하지 않음 | 화면에서 역할로 메뉴·버튼을 숨기되, 서버 403 처리도 구현해 둔다 |
| 페이지네이션은 도메인별로 필요한 목록에만 적용(서버 ADR-032). 적용 전 목록은 `data.items` 전체를 고정 정렬로 반환 | 적용된 목록(입고·창고 발주·공급처 발주서·지점 발주·출고·재고 할당·재고 5종)은 `page`·`size`·`sort`를 서버에 보내고 `PagedData`·`usePaging`·`SortableHead`·`Pager`(`components/common/list-paging.tsx`)를 쓴다. 정렬은 서버 sort로만 하고 필터·정렬 변경 시 page를 1로 돌린다. 나머지 목록은 계속 클라이언트에서 처리 |
| 날짜·시각에 오프셋 없음, KST 기준 (`2026-10-05T14:30:00`) | 시간대 변환 없이 그대로 표시·전송한다 |
| `errors[]`는 요청 본문 검증 실패에만 채워짐 | 비즈니스 오류(409)는 `message`와 `errorCode`로 안내한다 |
| 존재하지 않는 필터 값은 일부 API에서 404, 일부는 빈 목록 | 서버 문서의 해당 엔드포인트 항목을 따른다 |

## 3. 화면 처리 원칙

- **비활성화·재활성화**는 별도 버튼과 확인 다이얼로그로 둔다(`deactivate`/`activate`, 토글 아님). 창고를 재활성화해도 구역은, 상품을 재활성화해도 SKU는 자동 복구되지 않는다.
- **409 `CONFLICT`**: 이미 전이된 상태에 같은 요청을 보낸 경우가 많다. 안내 후 목록·상세를 다시 조회한다.
- **상태 전이 버튼**은 현재 상태에서 가능한 것만 보이게 한다. 사유(`reason`, ≤500자)가 필수인 전이는 입력 모달을 거친다.
- **원가·매입가 필드**는 점주 응답에서 빠지므로 optional로 다룬다.
- **이름 혼동 주의**: `/purchase-orders`는 창고 → 본사 발주 요청(공급처는 본사가 확정할 때 지정), `/supplier-orders`는 확정으로 생기는 공급처 발주서, `/orders`는 지점 → 창고 발주다. 라우트·폴더·화면 이름에서 구분한다.

## 4. 에러 코드 안내문구

서버는 `errorCode`마다 한국어 기본 메시지를 내려준다(wms-server `ErrorCode` + 도메인별 `*ErrorCode` enum). 그래서 화면은 **서버 `message`를 그대로 보여주는 것이 기본**이고, 서버 메시지만으로 부족한 코드만 `app/lib/api/error-messages.ts`의 `ERROR_GUIDES`에 안내문구를 둔다. 화면에서는 `getErrorMessage(error, 기본문구)`로 꺼낸다.

| errorCode | 이유 | 화면 처리 |
|---|---|---|
| `UNAUTHORIZED`, `FORBIDDEN`, `CONFLICT`, `INTERNAL_ERROR` | 공통 코드의 기본 메시지는 행동을 안내하지 않음 | 클라이언트 문구 |
| `SECTION_CAPACITY_EXCEEDED` | 입고 완료·재고 증량 시 발생. 서버 메시지에 다음 행동이 없음 | 다른 구역 선택 유도 |
| `STALE_QUANTITY` | 서버 메시지로 충분 | 메시지 표시 + 화면에서 현재 수량을 다시 조회 |
| `INSUFFICIENT_STOCK` | 서버 메시지에 SKU별 요청·가용 수량이 담김 | 메시지 그대로 노출 |
| `ORDER_IN_PICKING` | 서버 메시지로 충분 | 메시지 표시 |

코드가 필요 이상으로 늘지 않게, 서버 메시지로 충분하면 매핑하지 않는다.

공통 컴포넌트: `ReasonDialog`(사유 입력, ≤500자), `ConfirmDialog`(확인), `StatusBadge`(상태·진행 단계 배지) — `app/components/common/`.

## 5. 연동 현황

| 도메인 | 서버 API | 클라이언트 | 비고 |
|---|---|---|---|
| 상품 (브랜드·카테고리·상품·SKU·옵션) | 구현 | 완료 | 상품·SKU 비활성화·재활성화는 목록 행 버튼(본사 관리자). 상품을 재활성화해도 SKU는 자동 복구되지 않는다. 상품·SKU·브랜드·카테고리 등록은 모두 상품 화면 상단의 등록 버튼으로 여는 모달이다(본사 관리자만 버튼이 보인다). 브랜드는 영문 3자 코드를 직접 입력하고(서버가 대문자로 저장, 코드 없는 기존 브랜드에는 수정에서 한 번만 지정), SKU 단위는 서버 허용 목록(`GET /products/skus/units`: EA·BOX·SET, ADR-024) 드롭다운이고 목록 밖 값은 400이다. 이미 저장된 SKU의 단위는 변환되지 않는다. 서버에 비활성화·재활성화 API가 없고 카테고리 코드·상위는 수정 불가. SKU 등록은 매입·공급 단가 필수(0 허용). SKU 수정(`PATCH /products/skus/{skuId}`)은 본사 관리자만, 바뀐 필드만 전송. 카테고리 코드도 영문 3자(대문자 저장)다. 카테고리별 옵션 그룹 지정(ADR-025, 서버 #241 브랜치 기준)은 카테고리 목록의 "옵션 지정"(본사 관리자)에서 스펙/SKU 용도로 교체 저장하고 상위 지정은 읽기 전용이며, 옵션 그룹·값(코드 필수 영문·숫자 1~10자) 등록도 같은 다이얼로그에 있다. 상품 등록은 카테고리의 스펙 그룹마다 값 하나씩(`specOptionValueIds`), SKU 등록은 SKU 옵션 그룹마다 값 하나씩(`optionValueIds`) 고른다. 상품 코드(`브랜드코드-카테고리코드-일련번호`)와 SKU 코드·이름(옵션 코드·값 조합)은 서버가 발급해 입력란이 없고(ADR-026) 등록 직후 응답 값을 보여 준다. 브랜드 코드가 없는 기존 브랜드는 상품 등록이 409(`BRAND_CODE_REQUIRED`)라 선택해도 등록 버튼을 막고 안내하며, 코드가 없는 옵션 값은 SKU 옵션 선택지에서 뺀다. SKU 목록의 "옵션" 버튼은 옵션이 없는 기존 SKU에 한 번만 연결할 때 쓴다. 상품 수정 화면은 없어 `specOptionValueIds` 교체·카테고리 잠김은 화면에 반영하지 않았다. 단가 이력 조회 API는 서버에 없음 |
| 창고 (창고·구역·관리자 배정) | 구현 | 완료 | 창고·구역 비활성화·재활성화와 구역 삭제는 창고 상세에서 본사 관리자가 한다(구역은 창고를 재활성화해도 자동 복구되지 않음). 담당자 배정은 창고 상세(본사 관리자)에서 한다. 등록 시 수용량 필수(0 허용), 수용량 수정은 창고 상세에서 본사 관리자가 한다(창고·구역 정보 수정 화면은 없음). 창고 코드는 서버가 주소의 시·도로 발급(`WH-SU-001`)하므로 등록 화면에 입력란이 없다 |
| 재고 (구역×SKU 현황·집계·로트·이력·조정·부족재고) | 구현 | 완료 | `LotDetail.inbounds` 타입은 입고 연동 때 확정. 로트 상태 변경(격리·해제·폐기)은 본사 관리자만, 로트 마스터 탭에서 한다 |
| 지점 (지점·점주 배정) | 구현 | 완료 | 재활성화는 지점 상세에서 본사 관리자가 한다. 점주는 `/stores/my`로 본인 지점만 조회. 지점 코드는 서버가 주소의 시·도로 발급(`ST-BS-002`)하므로 등록 화면에 입력란이 없고, 수정에서 다른 시·도로 바꾸면 코드가 재발급된다 |
| 공급처 | 구현 | 완료 | 재활성화는 공급처 상세에서 본사 관리자가 한다. 창고 관리자는 서버가 활성 공급처만 반환(상태 필터 숨김). 발주 등록에서는 공급처를 고르지 않는다(확정 때 본사가 지정). 공급처 목록의 창고 관리자 접근 권한은 서버가 이번에 바꾸지 않았다 |
| 창고 발주 요청 (`/purchase-orders`) | 구현 | 완료 | 서버 이슈 #266(ADR-030) 반영. 등록은 창고 관리자가 SKU·수량만, 확정·반려는 본사 관리자만. 확정 화면에서 라인별 공급처를 고르고(후보는 `GET /products/skus/{skuId}/suppliers`) 공급처별 발주서 미리보기를 보여 준다. 반려(`REJECTED`)·반려 사유 표시 추가. 목록 페이지네이션·서버 정렬 적용 |
| 입고 (`/inbounds`) | 구현 | 완료 | 검수는 항목 전체 교체 방식. 등록은 공급처 발주서 상세에서(`supplierOrderId`), 검수 라인 후보는 그 발주서의 라인. 목록 페이지네이션·서버 정렬 적용 |
| 공급처 발주서 (`/supplier-orders`) | 구현 | 완료 | 조회 전용(목록·상세). 상태는 입고 완료·요청 취소 결과로만 바뀜. 창고 관리자는 담당 창고만. 목록 페이지네이션·서버 정렬 적용 |
| SKU↔공급처 매핑 (`/products/skus/{skuId}/suppliers`) | 조회만 구현 | 진행 중 | 확정 화면의 후보 조회에만 사용. 등록·삭제 화면은 별도 이슈 |
| 지점 발주 (`/orders`) | 12개 구현 | 완료 | 목록은 본사 관리자 `GET /orders`, 점주·창고 관리자 `GET /orders/my`(서버가 담당 범위로 좁힘, 본사 호출 시 403). 라우트는 `/store-orders`. 목록 페이지네이션·서버 정렬 적용(진행 단계는 계산 값이라 정렬 불가, 항목 수·총액은 정렬 가능) |
| 출고·재고 할당 | 구현 | 완료 | 할당·출고 생성은 지점 발주 상세에서. 둘 다 `skuIds`로 SKU를 골라 처리하고, 할당은 부분 할당(`shortages[]`을 결과에 표시). 재고 차감은 피킹 완료 시점. 출고·할당 목록은 페이지네이션·서버 정렬 적용(출고 생성 다이얼로그의 할당 조회는 `size: 100`) |
| 공통 기반 (현재 사용자, 에러 매핑, 공통 컴포넌트, 역할별 사이드바) | - | 완료 | |
| 인증 | 로그인(#31)·가입·비밀번호 변경(#33)·사용자 관리(#34) 완료 | - | 가입 승인은 사용자 목록에서 창고(창고 관리자)·지점(점주)을 반드시 함께 골라, 재활성화는 필요할 때만 골라 `PATCH /users/{id}`의 `warehouseId`/`storeId`로 보낸다. 서버가 승인 전 배정 API를 409로 막아, 담당자·점주 배정 목록에는 활성 사용자만 나온다 |

연동 순서: 지점 + 공급처 → 창고 발주·입고 → 지점 발주 → 출고·할당. (인증만 서버 선행 필요)
