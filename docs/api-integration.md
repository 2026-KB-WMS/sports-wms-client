# API 연동 가이드 (프론트 쪽 합의)

API 계약 본문은 wms-server의 `docs/api/*.md`가 기준이다([README](../README.md#api-계약-서버-문서가-기준) 참고). 이 문서는 **서버 문서에 없는 프론트 쪽 합의와 연동 현황**만 적는다. 서버 문서의 내용을 복제하지 않는다.

## 1. 코드 규칙

- `app/lib/api/<도메인>.ts`: 엔드포인트 함수와 요청·응답 타입. 서버 명세의 필드명을 그대로 쓴다(camelCase).
- `app/features/<도메인>/hooks.ts`: TanStack Query 훅. 쿼리 키는 `["도메인", 리소스, 조건]`.
- `app/features/<도메인>/*-page.tsx`: 화면. 라우트는 `app/routes.ts`에 등록한다.
- 호출은 `apiClient`만 쓰고(응답 봉투는 이미 벗겨짐), 오류는 `ApiError`(`statusCode`, `errorCode`, `fieldErrors`)로 다룬다.
- 4xx는 재시도하지 않는다(`query-client.ts`).

## 2. 서버 현황에 따른 임시 처리

서버가 아직 구현하지 않은 부분을 프론트가 어떻게 다루는지 정해 둔다. 서버가 바뀌면 이 절을 갱신한다.

| 서버 현황 | 프론트 처리 |
|---|---|
| 인증(JWT)·회원 도메인 미구현. `SecurityConfig`가 전체 허용 | `Authorization` 헤더 없이 호출. 헤더 추가 위치는 `client.ts`의 `buildHeaders` |
| 처리 사용자를 쿼리 파라미터 `userId`로 받음 (재고 조정, 입고 검수·완료, 지점 발주·출고 상태 전이, `/warehouses/my`, `/stores/my`) | 호출부에서 직접 넘긴다. **현재 사용자 모듈(`useCurrentUser`)을 만들어 한 곳에서 공급하는 것으로 정리 예정**(JWT 도입 시 이 모듈만 교체) |
| 역할별 403이 동작하지 않음 | 화면에서 역할로 메뉴·버튼을 숨기되, 서버 403 처리도 구현해 둔다 |
| 페이지네이션 보류. 목록은 `data.items` 전체를 고정 정렬로 반환 | 필터는 서버 쿼리 파라미터로, 정렬·페이징은 클라이언트에서 처리. 도입 시 `ListData`에 `pageInfo`를 추가하고 훅만 바꾼다 |
| 날짜·시각에 오프셋 없음, KST 기준 (`2026-10-05T14:30:00`) | 시간대 변환 없이 그대로 표시·전송한다 |
| `errors[]`는 요청 본문 검증 실패에만 채워짐 | 비즈니스 오류(409)는 `message`와 `errorCode`로 안내한다 |
| 존재하지 않는 필터 값은 일부 API에서 404, 일부는 빈 목록 | 서버 문서의 해당 엔드포인트 항목을 따른다 |

## 3. 화면 처리 원칙

- **비활성화는 단방향**이다(ACTIVE → INACTIVE, 재활성화 API 없음). 토글이 아니라 "비활성화" 버튼으로 둔다. 상품은 `PATCH`로 `isActive`를 바꾸지만 하위 SKU가 함께 비활성화되고 자동 복구되지 않는다.
- **409 `CONFLICT`**: 이미 전이된 상태에 같은 요청을 보낸 경우가 많다. 안내 후 목록·상세를 다시 조회한다.
- **상태 전이 버튼**은 현재 상태에서 가능한 것만 보이게 한다. 사유(`reason`, ≤500자)가 필수인 전이는 입력 모달을 거친다.
- **원가·매입가 필드**는 점주 응답에서 빠지므로 optional로 다룬다.
- **이름 혼동 주의**: `/purchase-orders`는 창고 → 공급처 발주, `/orders`는 지점 → 창고 발주다. 라우트·폴더·화면 이름에서 구분한다.
- 서버 미구현 기능은 UI를 만들지 않는다: 구역 `DELETE`, `GET /orders/my`.

## 4. 에러 코드 안내문구

도메인별 409 코드는 서버 문서에 있다. 사용자에게 서버 메시지만으로 부족한 코드는 아래에 안내문구를 정해 두고, 구현 시 `lib/api`의 매핑 테이블로 옮긴다.

| errorCode | 발생 위치 | 화면 처리 |
|---|---|---|
| `STALE_QUANTITY` | 재고 조정 | 현재 수량을 다시 조회해 보여주고 재입력을 유도 |
| `SECTION_CAPACITY_EXCEEDED` | 입고 완료, 재고 증량 조정 | 구역 수용량 초과 안내, 다른 구역 선택 유도 |
| `INSUFFICIENT_STOCK` | 재고 할당 | 메시지의 SKU별 요청·가용 수량을 그대로 노출 |
| `ORDER_IN_PICKING` | 발주 취소·보류 | 피킹이 시작되어 불가함을 안내 |

(필요한 코드가 생기면 행을 추가한다.)

## 5. 연동 현황

| 도메인 | 서버 API | 클라이언트 | 비고 |
|---|---|---|---|
| 상품 (브랜드·카테고리·상품·SKU·옵션) | 구현 | 완료 | |
| 창고 (창고·구역·관리자 배정) | 구현 | 완료 | 구역 `DELETE` 서버 미구현 |
| 재고 (집계·로트·이력·조정·부족재고) | 구현 | 완료 | `LotDetail.inbounds` 타입 미확정 → 입고 연동 때 확정 |
| 지점 (지점·점주 배정) | 구현 | 미착수 | 사이드바 "지점" 비활성 |
| 공급처 | 구현 | 미착수 | |
| 창고 발주 (`/purchase-orders`) | 구현 | 미착수 | |
| 입고 (`/inbounds`) | 구현 | 미착수 | 검수는 항목 전체 교체 방식 |
| 지점 발주 (`/orders`) | 11개 구현 | 미착수 | `GET /orders/my` 보류 |
| 출고·재고 할당 | 구현 | 미착수 | |
| 인증 | 미구현 | - | 서버 선행 필요 |

연동 순서: 지점 + 공급처 → 창고 발주·입고 → 지점 발주 → 출고·할당.
