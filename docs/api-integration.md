# API 연동 가이드 (프론트 쪽 합의)

API 계약 본문은 wms-server의 `docs/api/*.md`가 기준이다([README](../README.md#api-계약-서버-문서가-기준) 참고). 이 문서는 **서버 문서에 없는 프론트 쪽 합의와 연동 현황**만 적는다. 서버 문서의 내용을 복제하지 않는다.

## 1. 코드 규칙

- `app/lib/api/<도메인>.ts`: 엔드포인트 함수와 요청·응답 타입. 서버 명세의 필드명을 그대로 쓴다(camelCase).
- `app/features/<도메인>/hooks.ts`: TanStack Query 훅. 쿼리 키는 `["도메인", 리소스, 조건]`.
- `app/features/<도메인>/*-page.tsx`: 화면. 라우트는 `app/routes.ts`에 등록한다.
- 호출은 `apiClient`만 쓰고(응답 봉투는 이미 벗겨짐), 오류는 `ApiError`(`statusCode`, `errorCode`, `fieldErrors`)로 다룬다.
- 4xx는 재시도하지 않는다(`query-client.ts`).

## 2. 서버 현황에 따른 임시 처리

서버가 아직 구현하지 않은 부분을 프론트가 어떻게 다루는지 정해 둔다. 서버가 바뀌면 이 절을 갱신한다.

| 서버 현황 | 프론트 처리 |
|---|---|
| 인증(JWT) 로그인 연동 완료(#31). 토큰은 `app/lib/auth-token.ts`가 저장하고 `client.ts`가 `Authorization: Bearer`로 붙인다 | 401은 토큰 삭제 후 `/login`으로 이동(`AuthGate`). 로그인·가입의 401은 제외 |
| ~~처리 사용자를 쿼리 파라미터 `userId`로 받음~~ → 서버가 토큰에서 채움(#170) | 클라이언트는 `userId`를 보내지 않는다(#32). `/warehouses/my`·`/stores/my`도 토큰 기준이다. `useCurrentUser()`는 화면 표시·작성자 비교용 사용자 정보만 준다 |
| `GET /orders/my` 미구현 (인증 연동 때 소속 범위를 서버가 판별) | 지점 발주 목록은 `GET /orders`를 쓰되 점주는 `storeId`(`/stores/my`), 창고 관리자는 `warehouseId`(`/warehouses/my`)로 좁힌다. 인증이 붙으면 `/orders/my`로 교체 |
| 역할별 403이 동작하지 않음 | 화면에서 역할로 메뉴·버튼을 숨기되, 서버 403 처리도 구현해 둔다 |
| 페이지네이션 보류. 목록은 `data.items` 전체를 고정 정렬로 반환 | 필터는 서버 쿼리 파라미터로, 정렬·페이징은 클라이언트에서 처리. 도입 시 `ListData`에 `pageInfo`를 추가하고 훅만 바꾼다 |
| 날짜·시각에 오프셋 없음, KST 기준 (`2026-10-05T14:30:00`) | 시간대 변환 없이 그대로 표시·전송한다 |
| `errors[]`는 요청 본문 검증 실패에만 채워짐 | 비즈니스 오류(409)는 `message`와 `errorCode`로 안내한다 |
| 존재하지 않는 필터 값은 일부 API에서 404, 일부는 빈 목록 | 서버 문서의 해당 엔드포인트 항목을 따른다 |

## 3. 화면 처리 원칙

- **비활성화는 단방향**이다(ACTIVE → INACTIVE, 재활성화 API 없음). 토글이 아니라 "비활성화" 버튼으로 둔다. 상품은 `PATCH`로 `isActive`를 바꾸지만 하위 SKU가 함께 비활성화되고 자동 복구되지 않는다.
- **409 `CONFLICT`**: 이미 전이된 상태에 같은 요청을 보낸 경우가 많다. 안내 후 목록·상세를 다시 조회한다.
- **상태 전이 버튼**은 현재 상태에서 가능한 것만 보이게 한다. 사유(`reason`, ≤500자)가 필수인 전이는 입력 모달을 거친다.
- **원가·매입가 필드**는 점주 응답에서 빠지므로 optional로 다룬다.
- **이름 혼동 주의**: `/purchase-orders`는 창고 → 공급처 발주, `/orders`는 지점 → 창고 발주다. 라우트·폴더·화면 이름에서 구분한다.
- 서버 미구현 기능은 UI를 만들지 않는다: 구역 `DELETE`.

## 4. 에러 코드 안내문구

서버는 `errorCode`마다 한국어 기본 메시지를 내려준다(wms-server `ErrorCode` + 도메인별 `*ErrorCode` enum). 그래서 화면은 **서버 `message`를 그대로 보여주는 것이 기본**이고, 서버 메시지만으로 부족한 코드만 `app/lib/api/error-messages.ts`의 `ERROR_GUIDES`에 안내문구를 둔다. 화면에서는 `getErrorMessage(error, 기본문구)`로 꺼낸다.

| errorCode | 이유 | 화면 처리 |
|---|---|---|
| `UNAUTHORIZED`, `FORBIDDEN`, `CONFLICT`, `INTERNAL_ERROR` | 공통 코드의 기본 메시지는 행동을 안내하지 않음 | 클라이언트 문구 |
| `SECTION_CAPACITY_EXCEEDED` | 입고 완료·재고 증량 시 발생. 서버 메시지에 다음 행동이 없음 | 다른 구역 선택 유도 |
| `STALE_QUANTITY` | 서버 메시지로 충분 | 메시지 표시 + 화면에서 현재 수량을 다시 조회 |
| `INSUFFICIENT_STOCK` | 서버 메시지에 SKU별 요청·가용 수량이 담김 | 메시지 그대로 노출 |
| `ORDER_IN_PICKING` | 서버 메시지로 충분 | 메시지 표시 |

코드가 필요 이상으로 늘지 않게, 서버 메시지로 충분하면 매핑하지 않는다.

공통 컴포넌트: `ReasonDialog`(사유 입력, ≤500자), `ConfirmDialog`(확인), `StatusBadge`(상태·진행 단계 배지) — `app/components/common/`.

## 5. 연동 현황

| 도메인 | 서버 API | 클라이언트 | 비고 |
|---|---|---|---|
| 상품 (브랜드·카테고리·상품·SKU·옵션) | 구현 | 완료 | SKU 등록은 매입·공급 단가 필수(0 허용). SKU 수정(`PATCH /products/skus/{skuId}`)은 본사 관리자만, 바뀐 필드만 전송. 단가 이력 조회 API는 서버에 없음 |
| 창고 (창고·구역·관리자 배정) | 구현 | 완료 | 구역 `DELETE` 서버 미구현. 담당자 배정은 창고 상세(본사 관리자)에서 한다. 등록 시 수용량 필수(0 허용), 수용량 수정은 창고 상세에서 본사 관리자가 한다(창고·구역 정보 수정 화면은 없음) |
| 재고 (집계·로트·이력·조정·부족재고) | 구현 | 완료 | `LotDetail.inbounds` 타입은 입고 연동 때 확정 |
| 지점 (지점·점주 배정) | 구현 | 완료 | 점주는 `/stores/my`로 본인 지점만 조회 |
| 공급처 | 구현 | 완료 | 창고 관리자는 서버가 활성 공급처만 반환(상태 필터 숨김). 발주 등록의 공급처 선택은 창고 발주 이슈에서 사용 |
| 창고 발주 (`/purchase-orders`) | 구현 | 완료 | 등록은 창고 관리자만, 확정은 본사 관리자만. 입고 등록 버튼은 입고 연동 때 추가 |
| 입고 (`/inbounds`) | 구현 | 완료 | 검수는 항목 전체 교체 방식. 등록은 확정된 발주 상세에서 |
| 지점 발주 (`/orders`) | 11개 구현 | 완료 | `GET /orders/my` 보류 → 점주는 `storeId`, 창고 관리자는 `warehouseId`로 `GET /orders`를 좁혀 조회. 라우트는 `/store-orders` |
| 출고·재고 할당 | 구현 | 완료 | 할당·출고 생성은 지점 발주 상세에서. 재고 차감은 피킹 완료 시점 |
| 공통 기반 (현재 사용자, 에러 매핑, 공통 컴포넌트, 역할별 사이드바) | - | 완료 | |
| 인증 | 로그인(#31)·가입·비밀번호 변경(#33)·사용자 관리(#34) 완료 | - | - |

연동 순서: 지점 + 공급처 → 창고 발주·입고 → 지점 발주 → 출고·할당. (인증만 서버 선행 필요)
