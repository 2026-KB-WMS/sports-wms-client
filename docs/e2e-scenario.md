# 프론트 e2e 수동 시나리오

초기 본사 관리자가 만들어진 직후부터 **화면만으로** 업무 흐름 전체를 한 바퀴 도는 수동 점검 순서다. 서버 쪽 API 시나리오(`wms-server/docs/scenario/e2e.md`, 스크립트 기반)를 화면 조작 기준으로 옮긴 것이며, 기대 수량은 그 문서와 같다. 응답의 기준은 서버 `docs/api/*.md`이고, 이 문서와 다르면 서버 문서를 따른다.

- 타입체크·빌드 통과는 동작 확인이 아니다. 이 시나리오를 실제로 돌려 본 결과만 "확인"으로 적는다.
- 각 단계의 **확인** 항목이 어긋나면 그 자리에서 멈추고 어느 단계인지 기록한다.

## 0. 준비

1. 깨끗한 DB로 서버를 띄운다. 최초 본사 관리자는 환경변수로 만들어진다([ADR-013](../../wms-server/docs/adr/013-initial-hq-admin-from-environment.md)).

   | 환경변수 | 규칙 |
   |---|---|
   | `WMS_ADMIN_LOGIN_ID` | 소문자 4~20자 |
   | `WMS_ADMIN_PASSWORD` | 8자 이상, 영문·숫자·특수문자 |
   | `WMS_ADMIN_NAME`, `WMS_ADMIN_EMAIL`, `WMS_ADMIN_PHONE` | 비어 있지 않은 값 |

   하나라도 비면 관리자가 만들어지지 않는다(기동은 됨, 로그에 오류).
2. `npm run dev` → `http://localhost:5173`. `/api`는 `localhost:8080`으로 프록시된다.
3. **브라우저 프로필·창을 역할별로 나눈다**(본사 / 창고 관리자 / 점주). 로그아웃을 반복하면 토큰 만료·상태 혼동이 생긴다. 시크릿 창 2개 + 일반 창 1개를 권장한다.

## 1. 쓸 데이터 (이름은 예시)

| 구분 | 값 |
|---|---|
| 창고 | W1 (수용량 10000), W2 (수용량 1000) |
| W1 구역 | A (일반, 3000), B (일반, 3000), D (불량, 500) |
| W2 구역 | A2 (일반, 500) |
| 지점 | S1, S2 |
| 사용자 | 창고 관리자 `wm1`(→W1), `wm2`(→W2), 점주 `own1`(→S1), `own2`(→S2) |
| 상품 | 브랜드 1, 카테고리 1, 상품 1, SKU1(매입 1000 / 공급 1500), SKU2(매입 2000 / 공급 3000) |
| 공급처 | 1개 |

규칙: 구역 수용량 합은 창고 수용량 이하여야 한다. SKU 단가는 등록 시 필수(0 허용).

## 2. 본사 관리자: 기준 정보 세팅

로그인: `/login` → 환경변수의 관리자 계정. 사이드바에 모든 메뉴(상품·창고·공급처·…·사용자)가 보여야 한다.

| # | 화면 | 조작 | 확인 |
|---|---|---|---|
| 2-1 | `/login` | 관리자 로그인 | `/`로 이동, 사이드바 하단에 이름·역할 표시 |
| 2-2 | `/warehouses` | **새 창고 등록**: W1(수용량 10000), W2(1000) | 목록에 2건, 상태 활성 |
| 2-3 | `/warehouses/{id}` (W1) | **새 구역 등록**: A·B(일반), D(불량) | 구역 3건. 수용량 합 초과 시 오류 안내 |
| 2-4 | `/warehouses/{id}` (W2) | 구역 A2 등록 | 구역 1건 |
| 2-5 | `/stores` | **새 지점 등록**: S1, S2 | 목록에 2건 |

## 3. 사용자 가입 → 소속 배정 → 승인

순서가 중요하다. **승인 전에 소속을 먼저 배정**해야 한다(소속 없는 상태로 `ACTIVE` 시도 시 409 `AFFILIATION_REQUIRED`).

| # | 화면 | 조작 | 확인 |
|---|---|---|---|
| 3-1 | `/signup` (로그아웃 상태) | `wm1`, `wm2`는 역할 창고 관리자, `own1`, `own2`는 점주로 4명 가입 | 가입 성공, 로그인 시도하면 승인 대기로 거절 |
| 3-2 | `/signup` | 이미 쓴 로그인 ID로 다시 가입 | 409 `DUPLICATE_LOGIN_ID` 메시지 |
| 3-3 | `/users` (본사) | 상태 필터 기본값 "승인 대기"에 4명이 보임 | 4건 |
| 3-4 | `/warehouses/{id}` | W1 상세 **담당자 배정**에서 `wm1`, W2 상세에서 `wm2` | 담당자 목록에 반영(승인 대기 사용자도 선택 가능) |
| 3-5 | `/stores/{id}` | S1 상세 **점주·담당자 배정**에서 `own1`, S2에서 `own2` | 목록에 반영 |
| 3-6 | `/users` | 소속 배정 전 사용자 하나를 먼저 승인 시도(선택) | 409 `AFFILIATION_REQUIRED` 안내. 이후 배정 → 승인 |
| 3-7 | `/users` | 4명 모두 **승인** | 상태 활성 |
| 3-8 | 각 창(시크릿) | `wm1`, `own1`로 로그인 | `wm1`: 창고·공급처·창고 발주·입고·재고·재고 할당·출고·지점 발주 + 상품. `own1`: 상품·지점·지점 발주만(창고 메뉴 없음) |

## 12. 서버 e2e와 다른 점 (화면에서 못 하는 것)

- 서버 시나리오의 **400 검증 케이스**(합격+불량≠입고, 피킹 수량 초과, `categoryCode` 수정, `EXPIRED`로 상태 변경)는 폼이 먼저 막거나 UI에 해당 입력이 없어 화면에서 재현되지 않는다. 서버 스크립트로 확인한다.
- 동시성(같은 로트에 동시 입고·할당)은 범위 밖이다.
